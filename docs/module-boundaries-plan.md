# 按用户任务划分模块：迁移与验收计划

基线：`e3d1bcb`，2026-11-25。状态：待实施。总跟踪：[GitHub #150](https://github.com/Zhou-chu/thu-campus-mcp/issues/150)。**保留单仓、现有服务包和外部契约；每批交付一条能从入口走到结果的用户旅程。** 先修会影响校园写入结果的缺陷，不把拆目录或引入通用框架作为里程碑。

## 1. 谁负责什么

| 边界 | 责任与依赖 | 不做什么 |
| --- | --- | --- |
| Web、HTTP、MCP 与移动端入口 | 解析输入、认证和入口授权、呈现结果；按用户动作调用用例。HTTP 可绑定确认令牌与参数，MCP 要明确由哪一层取得本次授权。 | 不自行定义成功、补偿、重试。不同客户端不必共享页面组件。 |
| 按任务组织的用例 | 体育：锁场、下单、补偿、查询；座位：列出本人预约、确认目标、取消、核对；课表：读取、解析、合并本地课；对话：用户会话、模型调用及记录。作业、定时任务维持现状，未来各按自己的动作迁移。 | 不导入 DOM、HTTP 路由、MCP SDK 或具体浏览器；不把体育和座位硬并为预约引擎。 |
| 适配器与装配 | 保留校园 SDK/浏览器、模型和存储实现；由应用服务装配依赖。适配器翻译上游回执，保留区分明确拒绝与响应未知的证据。 | 不把“HTTP 成功”“进程退出”解释为校园业务成功；不为所有服务加统一写重试。 |

迁移方式：先在原接口后抽取能注入外部调用的单个用例；让现有调用方委托给它，再移除旧分支。HTTP 路径、MCP 工具名、已发布参数与确认要求保持兼容。每个模块移交时列出入口、授权方、可观测结果和只读核对方式。只有出现第二个确实需要同一机制的模块才提取共享实现。Web 只随旅程迁出相关事件和状态，不整体搬运主脚本。

## 2. 分批实施

| C2 · [邮箱首轮对话 #149](https://github.com/Zhou-chu/thu-campus-mcp/issues/149) | 在真实邮箱浏览器会话贯通服务状态、首条流式消息与刷新回读。 | 不注入设备令牌；状态卡区分可用、需登录、需人工验证；模型替身收到一次请求，用户看见正文，刷新后记录仍在。CSRF 拒绝时零次模型调用。 |

顺序：A 优先；B 交付写用例样板后再决定是否推广，而非强迫其他模块照搬。C1 与 C2 可并行。风险或产品入口有分歧时，只暂缓该入口，不绕过授权、不把未知改成成功。

## 3. 验收证据与发布边界

1. **用例层**用可计数的适配器替身验证写入、补偿次数、参数绑定和失败分支。详细复现见[体育预约缺陷记录](../issues/BUG-002-sports-unlock.md)。
2. **本地用户旅程**用真实 Chromium、应用 HTTP 路由、Cookie 和会话读写；可用测试数据库与受控校园/模型替身。验证用户看见的结果和刷新后状态，而不只断言 HTTP 200。窄屏是浏览器视口，不是手机实机验收。
3. **批末门禁**保留现有五条分层检查；先跑受影响测试，批末按 CI 检查覆盖率与质量门，报告工具、范围和实测数值（仓库要求均不低于 90，二者口径不同）。不要每次移动代码就跑全套，也不以绿灯代替用户旅程。每批对应独立可回退的提交或 PR，不混入无关迁移。
4. **线上证据另列**：能力清单分别标记“代码接入 / 入口开放 / 本地旅程验证 / 线上已核验”。经授权可低频只读核验；真实占位、取消、支付均不进 CI，不以计划或本地测试代替逐次授权。手机实机验证继续暂停。
